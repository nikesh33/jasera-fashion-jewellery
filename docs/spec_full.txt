1. Executive Summary
This document defines the complete frontend development specification for Suvarna, a premium Indian heirloom jewellery e-commerce platform to be built for a local jewellery seller. Suvarna will sell earrings, jhumkas, bangles, rings, necklaces, bracelets, and curated jewellery sets, and is positioned to deliver a shopping experience inspired by established premium brands such as GIVA, CaratLane, and Tanishq while maintaining its own distinct brand identity rooted in Indian heritage and craftsmanship.
The proposed technology stack is Next.js 14 (App Router) with TypeScript for the frontend, Tailwind CSS for styling, TanStack Query for server-state caching, Zustand for client UI state, shadcn/ui as the component primitive layer, react-hook-form for form management, and zod for schema validation shared between client and backend. The frontend is designed to integrate with a Node.js + Express.js backend and a MySQL database through a versioned REST API contract documented in Section 12 of this specification.
Scope of this specification covers all eleven requirement areas requested by the client: customer-facing pages and routes; homepage, navigation, and product discovery; product listing and product detail; cart, wishlist, checkout, payment, authentication, account, order tracking, and order history; a complete admin dashboard; a premium visual design system; reusable React components and folder structure; state management, forms, validation, error handling, loading states, and accessibility; a REST API integration contract; frontend security responsibilities and the security controls that must be enforced by the backend; SEO, performance, mobile responsiveness, testing, and production deployment; and all important edge cases with acceptance criteria.
Beyond the eleven required areas, this document also includes a phase plan that distinguishes the MVP (launch-blocking) feature set from Phase 2 and Phase 3 enhancements, and a set of acceptance test cases written in Given/When/Then format covering the six critical customer and admin flows. These additions are intended to give the client and the eventual coding agent a clear, defensible scope boundary that prevents scope creep without sacrificing commercial completeness.
The intended audience of this document is the client (for sign-off) and an autonomous coding AI agent (for implementation). After client review and approval, this specification is designed to be converted into a final implementation prompt that the coding agent can execute against with minimal further clarification. Throughout the document, the keywords MUST, SHOULD, and MAY are used in the RFC 2119 sense to indicate requirement strength, and bracketed placeholders such as [CLIENT_NAME] or [PAYMENT_GATEWAY] indicate variables that must be confirmed with the client before the implementation prompt is finalised.
2. Project Context, Brand Identity & Scope Boundaries
2.1 Business Context
The client is a local Indian jewellery seller offering a catalogue spanning seven primary product categories: earrings, jhumkas (traditional bell-shaped earrings), bangles, rings, necklaces, bracelets, and complete jewellery sets. The business currently sells through offline channels and wishes to establish a premium online storefront that reflects the craftsmanship and heritage of its catalogue while operating as a real, revenue-generating e-commerce business — not a portfolio demo or a landing page. Every requirement in this specification is therefore framed against real-world commercial constraints: legal compliance, payment security, tax handling, fulfilment workflows, and customer support.
2.2 Proposed Brand Identity
In the absence of a final brand name from the client, this specification proposes the working brand name Suvarna, derived from the Sanskrit term for golden or of good colour. The name evokes heritage, premium positioning, and a clear connection to Indian jewellery tradition while remaining pronounceable, short, and brandable. The proposed tagline is Heirlooms, reimagined. — positioning the brand as both rooted in tradition and contemporary in execution. Should the client choose a different name, every visual and copy element in this specification is designed to be rebranded without architectural change; only string tokens and the logo asset require replacement.
The proposed brand palette is built around four core colours that signal premium Indian jewellery without copying any specific competitor: Deep Maroon (#5C1A2B) referencing traditional Indian bridal jewellery and the richness of red zariwork, Antique Gold (#B8893D) referencing the warmth of unpolished gold used in heirloom pieces, Ivory (#FAF6EE) as the canvas colour evoking raw silk and parchment, and Charcoal (#1F1F1A) as the primary text colour. A secondary Rose Gold (#C9A87C) is introduced for accent surfaces such as hover states and badges. The full design system is documented in Section 9.
2.3 Competitive Benchmark References
The following brands are referenced in this specification as competitive benchmarks only. Their mention does not authorise copying of any visual, copy, or code element; they are referenced solely to communicate the expected quality bar and user experience patterns. The benchmarks are: GIVA (premium positioning, minimalist product photography, clean PDP layout), CaratLane (robust filtering, virtual try-on ambitions, strong mobile checkout), Tanishq (heritage storytelling, trust badges, festive collection merchandising), and Bluestone (configurable ring filters, EMI presentation). Suvarna will establish its own distinct visual identity rather than imitating any of these.
2.4 Out-of-Scope for MVP
To preserve delivery quality and time-to-launch, the following features are explicitly excluded from the MVP and are not described as requirements in this specification. They are flagged here so the client and coding agent have a single source of truth for scope boundaries.
Native iOS and Android applications (mobile web is fully responsive and the site will be installable as a PWA in Phase 3).
Multi-vendor marketplace functionality (Suvarna is single-seller in MVP).
Live video shopping or influencer live-stream sessions.
Augmented-reality try-on in MVP (Phase 2 may include ring try-on for a single category).
B2B wholesale portal for retailers (Phase 3).
International shipping, multi-currency, and multi-language in MVP (English only at launch; Hindi in Phase 2; additional regional languages in Phase 3).
Loyalty programme, referral programme, and gift cards (Phase 3).
Subscription products and recurring billing.

3.2 Route Guards & Authentication
Routes marked Auth: Yes require an authenticated session. Unauthenticated visits MUST be redirected to /auth/login with the original destination preserved in a redirect_url query parameter (URL-encoded) and replayed after successful login. Routes marked Auth: Optional allow both guest and authenticated access; the implementation MUST gracefully merge guest cart and guest wishlist into the user account on login. The /order/confirm/[id] route is token-gated — the token is delivered via order confirmation email and SMS — to allow guest customers to view their own order without registration.
4. Homepage Layout, Navigation & Product Discovery
4.1 Homepage Anatomy
The homepage is the primary commercial surface and is organised as a vertical stack of merchandising blocks. Each block has a specific commercial intent and is fully manageable from the admin dashboard so that the client can refresh the storefront for festive seasons (Diwali, Akshaya Tritiya, Karva Chauth, wedding season) without engineering intervention. The blocks, top to bottom, are: (1) promo announcement bar (top of page, dismissible); (2) primary header; (3) hero carousel of three to five slides; (4) shop-by-category circular rail; (5) new-arrivals product rail; (6) editorial collection feature block (full-width image + caption); (7) bestsellers product rail; (8) festivity or seasonal feature block; (9) second product rail (e.g. under INR 5,000); (10) trust badges strip (genuine jewellery, certified, easy returns, secure payments); (11) customer testimonial carousel; (12) Instagram feed grid (Phase 2 social proof); (13) newsletter signup; (14) footer.
4.2 Header
The header is persistent across all storefront pages and is composed of four zones. Zone A is the top announcement bar (single line, dismissible per session via cookie) used for site-wide promotions such as festive offers, free shipping thresholds, or new collection launches. Zone B is the main header row containing (left to right): the mobile hamburger trigger, the logo, the primary navigation links (New In, Earrings, Jhumkas, Bangles, Rings, Necklaces, Bracelets, Sets, Collections, About), a search trigger that opens a full-screen overlay, and on the right the account icon, the wishlist icon with live badge count, and the cart icon with live badge count. Zone C is a secondary nav row visible only on category hover, showing sub-category quick links. Zone D is the sticky header shadow that appears on scroll.
4.3 Footer
The footer is divided into five columns: Shop (links to each category), Help (track order, contact, shipping, returns, size guide, FAQ), Company (about, careers, press, sustainability), Policies (privacy, terms, cookies, grievance officer per Indian e-commerce rules), and Contact (address, phone, email, hours, social icons). Below the columns: payment method icons (UPI, Visa, Mastercard, RuPay, Razorpay), a grievance officer note (required by Indian Consumer Protection (E-Commerce) Rules 2020), and the copyright line with the registered trademark symbol.
4.4 Search Experience
Search is triggered from the header and opens as a full-screen overlay with a large input auto-focused on open. The overlay surfaces four sections: (1) recent searches (last 8 stored in localStorage), (2) trending searches (admin-curated and algorithmically supplemented), (3) suggested products (instant results matching the typed query, displayed as a 2-column image grid), and (4) suggested categories (when the query matches a category name). Search queries are debounced at 250ms; suggestions are fetched from GET /api/v1/search/suggest. Pressing Enter navigates to /search?q=<query>. Empty search state shows the curated trending list.
4.5 Product Discovery Surfaces
Beyond the homepage rails, products are discoverable through four additional surfaces. Category and sub-category pages (Section 5) display products with filtering and sorting. Search results pages render the same product grid as PLPs but with a no-results state if no matches. The PDP (Section 5.4) displays related products (same category, same collection) and recently viewed products (last 10 stored in localStorage, synced to server for logged-in users). Wishlist and cart both surface inline product recommendations for cross-sell. Each discovery surface reuses the same ProductCard component (Section 10.2) to ensure consistent visual language.

5. Product Listing, Filtering, Sorting & Product Detail
5.1 Product Listing Page (PLP) Anatomy
The PLP serves three routes — /shop, /shop/[category], and /shop/[subCategory] — through a single shared component. Anatomy: (1) breadcrumb (Home / Shop / [Category]); (2) optional category banner with editorial copy; (3) result count and active filter chips; (4) sort dropdown (relevance, price low-to-high, price high-to-low, newest, best-selling, rating, discount); (5) filter sidebar (desktop) / filter bottom-sheet (mobile); (6) product grid (4 columns desktop, 3 columns tablet, 2 columns mobile); (7) pagination (12 per page) with infinite-scroll fallback for mobile; (8) empty state with suggested categories when no results; (9) SEO footer with category description and FAQs.

5.3 Sort Options
Sort options are: Relevance (default — admin-defined boost with a manual override per PLP), Price — Low to High, Price — High to Low, Newest (created_at desc), Best-Selling (units_sold desc, last 30 days), Top Rated (avg_rating desc, requires min 10 ratings), Discount (effective discount % desc). Selected sort is reflected in the URL search params to support shareable filtered URLs.
5.4 Product Detail Page (PDP) Anatomy
The PDP is the single highest-value page for conversion and is built with particular care. Anatomy: (1) breadcrumb; (2) two-column layout — left column image gallery (60% width), right column product information (40% width); (3) below the two-column area: tabbed content (Description, Specifications, Care Guide, Shipping & Returns), customer reviews with rating distribution and pagination, related products rail, recently viewed rail; (4) sticky mobile add-to-cart bar at viewport bottom.
5.4.1 Image Gallery
The image gallery includes a primary image area (4:5 aspect ratio) with hover-zoom on desktop and pinch-zoom on mobile, a vertical thumbnail strip on desktop (left of main image) and horizontal thumbnail strip on mobile (below main image), optional product video (autoplay muted on visible, tap to enable audio), and an AR try-on affordance (Phase 2 — rings only) when available. Every product MUST have at least 5 images: front, side, worn (lifestyle), detail close-up, and packaging. Images use the loading="lazy" attribute except for the first image, which uses priority loading for LCP.
5.4.2 Product Information Column
The right column displays: product title (H1), brand badge, rating summary (aggregate rating + review count linking to reviews section), price block (selling price, MRP with strikethrough, discount % in maroon), stock status ("In stock" / "Only N left" / "Out of stock — notify me"), short description (2–3 lines), variant selectors (size selector for rings and bangles with a size guide link; material selector if multiple material options exist; colour selector), quantity stepper (1–10, with backend enforcement of max-purchase-per-order), primary actions (Add to Cart — full-width antique-gold button; Buy Now — maroon button leading directly to /checkout; Wishlist — outline heart icon), secondary actions (Share — opens native share sheet on mobile, copy link on desktop; Pincode delivery check — shows estimated delivery date for entered pincode), trust microcopy (genuine certificate, easy 7-day returns, secure payments), and accordion of additional details.
5.4.3 PDP Tabs
The Description tab contains long-form product description, design story, and occasion recommendations. The Specifications tab is a key-value table (material, weight, gemstone, certification, dimensions, origin, purity). The Care Guide tab explains cleaning, storage, and wear guidance. The Shipping & Returns tab summarises shipping timelines, return policy, and exchange process. The reviews tab is described in Section 5.4.4.
5.4.4 Reviews Section
Reviews are critical social proof for premium jewellery. The section displays: aggregate rating (one decimal), total review count, rating distribution bar (5★ / 4★ / 3★ / 2★ / 1★ with percentages), sort options (most recent, most helpful, highest, lowest), filter by rating, review cards (reviewer name, verified-buyer badge, rating, date, review title, body, optional photos), and pagination or load-more. The Write-a-Review button opens a modal that accepts rating (mandatory), title, body, and up to 3 photos; submission requires a verified order and is throttled to one review per product per order.
5.4.5 PDP SEO Schema
Every PDP MUST embed schema.org Product JSON-LD with name, image (array), description, sku, brand (Organization with name Suvarna), offers (Offer with price, priceCurrency INR, availability, url, priceValidUntil), aggregateRating (ratingValue, reviewCount, bestRating 5), and BreadcrumbList. This enables rich results in Google Search and is a launch-blocking SEO requirement.

6. Cart, Wishlist, Checkout, Payment & Order Confirmation
6.1 Shopping Cart
The cart is the first revenue-bearing surface in the conversion funnel and is engineered to remove friction without compromising data integrity. The cart page renders line items as a list, each row showing product thumbnail (square 96px), product name (linked to PDP), variant summary (size, material, colour), unit price, MRP strikethrough, quantity stepper (1–10 with backend max-per-order enforcement), line total, and action menu (Move to Wishlist, Save for Later, Remove). Below the line items: coupon input field with Apply button, gift-wrap add-on checkbox (₹49), and a sticky order summary panel (right column on desktop, sticky bottom sheet on mobile) showing subtotal, applied discount, shipping (free over ₹2,000, else ₹99), tax (GST included in listed price per Indian norms), and grand total. Empty cart state shows a curated rail of bestsellers with a Shop Now CTA.
The cart MUST be persistent for both guest and authenticated users. For guest users the cart is stored in localStorage and merged into the server-side cart on login (merge strategy: union by product+variant, sum quantities capped at max-per-order). For authenticated users the cart is server-side via TanStack Query mutations with optimistic UI updates; the wishlist operates on the same pattern.
6.2 Wishlist
The wishlist is a grid view (4 columns desktop, 2 columns mobile) of saved products with each card supporting Move to Cart, Remove, and Add Note (private, for personal gifting reminders). Wishlist sharing is a Phase 2 enhancement — in the MVP the wishlist is private per user. For guests the wishlist is stored locally; on login it is merged into the server-side wishlist using a union-by-product+variant strategy.
6.3 Checkout — Three-Step Flow
Checkout is a three-step linear flow implemented as a single page with step indicators and forward/back navigation. The three steps are Address, Payment, and Review. The implementation MUST support both guest and authenticated checkout; an authenticated user pre-fills from their address book and order history, while a guest can complete the purchase without ever registering. A persistent order summary panel is visible on the right (desktop) or as a sticky bottom sheet (mobile) throughout all three steps so the customer always sees the total.
6.3.1 Step 1 — Address
If authenticated, the customer sees their saved address book as selectable radio cards plus an Add New Address affordance. If guest, the form to enter a new address is shown directly. The address form fields are India-specific: Full Name, Phone Number (with +91 prefix and 10-digit validation), Pincode (6-digit, with auto-fetch of city/state via the postal API), Address Line 1 (house no, building), Address Line 2 (street, area), Landmark (optional), City (auto-filled from pincode, editable), State (dropdown of 28 states + 8 UTs), Address Type (Home/Work/Other). Pincode serviceability is checked in real time; if a pincode is not serviceable the customer is shown a clear message and the flow is blocked with an explanation.
6.3.2 Step 2 — Payment Method
The payment method selection is radio-grouped into: UPI (with PhonePe, Google Pay, Paytm, BHIM sub-options and a UPI ID collect option), Credit/Debit Cards (with saved cards visible if authenticated — only card brand + last 4 digits + nickname are stored, never the full card number), Net Banking (drop-down of major banks), Wallets (Paytm, Mobikwik, Amazon Pay), EMI (Phase 2; in MVP show only on cart > ₹5,000 with credit-card EMI options), Cash on Delivery (gated by pincode serviceability). A coupon can be applied here if not already applied in cart. The order summary recalculates to reflect any shipping or COD charges.
6.3.3 Step 3 — Review & Place Order
The review step shows the final order: items with quantities and totals, shipping address (with edit link returning to step 1), payment method (with edit link returning to step 2), coupon summary, shipping, tax, and grand total. A final Place Order button triggers the payment initiation flow described in Section 6.4. A confirmation checkbox for terms acceptance (mandatory — links to /policies/terms) and an optional marketing opt-in are present.
6.4 Payment UI & Integration Pattern
Payment is the highest-risk integration in the application and is implemented to never touch raw card data on the frontend. The integration pattern is: (1) on Place Order click, the frontend calls POST /api/v1/checkout/payment/initiate with the order payload (items, address, payment method, coupon) and an idempotency key generated client-side; (2) the backend validates the order, computes final totals server-side, creates a pending order in MySQL, and returns a payment session URL or token from the payment gateway (Razorpay or Cashfree recommended for India); (3) the frontend either opens the hosted payment page (full redirect) or embeds the gateway's hosted fields in an iframe — never native inputs for card data; (4) after payment completion the gateway redirects to /order/confirm/[id] or shows a failure screen, and the frontend polls POST /api/v1/checkout/payment/verify to confirm the order status server-side; (5) on success the cart is cleared, the order confirmation page is rendered with order ID and estimated delivery, and a confirmation email and SMS are triggered by the backend.
6.5 Order Confirmation
The order confirmation page (/order/confirm/[id]) shows: success hero with order ID and a thank-you message, ordered items summary, shipping address, payment summary, estimated delivery date (computed by backend based on pincode and warehouse), Track Order button (links to /account/orders/[id] for authenticated users, or to /track-order for guests), Continue Shopping button, and a personalised cross-sell rail. This page is token-gated for guests via a query parameter token that is delivered by email/SMS and validated server-side; the token has a 24-hour TTL.
6.6 Checkout Edge Cases
The following edge cases MUST be handled gracefully by the frontend. (1) Payment gateway timeout — show a clear message with a Check Status button that polls the verify endpoint; do not allow a duplicate place-order attempt without confirmation. (2) Payment success but order creation failure — the backend reconciliation webhook from the gateway will recover the order; the frontend must show a Payment Received, Order Being Confirmed state and instruct the user to check email. (3) Address validation failure (pincode unserviceable) — block navigation to step 2 with an inline error and suggest alternative pincode if nearby areas are serviceable. (4) COD not available for pincode — hide COD option on step 2 dynamically based on the pincode serviceability response. (5) Coupon expired mid-session — show toast notification, recompute totals, allow user to proceed without coupon. (6) Price changed between cart and checkout — show a Price Change notice with the new total and require explicit Re-accept before placing the order. (7) Out-of-stock discovered at order creation — block with a clear message, return user to cart with the unavailable item flagged, and offer replacement suggestions.
7. Customer Authentication & Account Pages
7.1 Authentication Flows
Authentication uses a phone-OTP-first registration flow, which is the dominant pattern for Indian e-commerce and avoids the high friction of email verification before first purchase. The registration flow is: (1) customer enters full name, phone number (+91, 10 digits), password (min 8 chars, 1 letter, 1 number), and optional email; (2) frontend calls POST /api/v1/auth/otp/send which sends an SMS OTP; (3) customer enters the 6-digit OTP within 5 minutes; (4) frontend calls POST /api/v1/auth/register with the OTP to complete registration; (5) on success the backend returns access and refresh tokens and the frontend redirects to the intended redirect_url or /account. Login flow: customer enters phone or email + password; on success tokens are issued; on 3 consecutive failures the account is rate-limited for 5 minutes and the customer is shown a forgot-password link.
Forgot password flow: customer enters registered phone or email; an OTP is sent; on OTP verification a reset-password form is shown; on submit the backend updates the password and invalidates all existing sessions. Email verification is a Phase 2 enhancement; in MVP, email is optional and unverified. Social login (Google, Facebook) is a Phase 2 enhancement. Session persistence uses an access token (15-minute TTL) stored in memory (Zustand) and a refresh token (7-day TTL) stored in an httpOnly, secure, sameSite=lax cookie set by the backend; the frontend never reads the refresh token directly. On access-token expiry, the next request transparently calls POST /api/v1/auth/refresh which uses the refresh-token cookie to issue a new access token; on refresh failure the user is redirected to login.
7.2 Account Dashboard
The account dashboard (/account) is the landing page after login and shows an overview: profile summary card, recent orders (last 5 with status badges), default address, wishlist count, saved coupons, and quick links. The left sidebar (collapsible on mobile to a drawer) provides navigation to all account sub-pages.
7.2.1 Profile
The profile page (/account/profile) shows first name, last name, email (with verified/unverified badge), phone (with verified badge), gender (optional, used for gifting personalisation), date of birth and wedding anniversary (optional, used for gifting prompts and birthday discount). All fields are editable through inline forms with optimistic UI and confirmation toasts. Personal data is treated as PII per Section 13 — the frontend must mask phone and email in any display that is not the profile-edit form itself.
7.2.2 Addresses
The addresses page (/account/addresses) is a CRUD interface for the address book with the same India-specific fields as Section 6.3.1. Each address card shows a default badge, edit, delete, and set-as-default actions. Deletion of an address used by a pending order is blocked with an explanatory message.
7.2.3 Orders & Order Tracking
The orders list (/account/orders) is a paginated table of past orders showing order ID, date, item count, total, status badge, and a View Detail link. The order detail page (/account/orders/[id]) shows: order summary, items with images and individual totals, shipping address, payment method and summary, and a status timeline. The status timeline is a vertical stepper with completed steps filled in maroon and the current step pulsing. The standard timeline stages are Placed → Confirmed → Packed → Shipped → Out for Delivery → Delivered. Returns and cancellations show on a parallel timeline. An Invoice download button (PDF generated by the backend) and a Reorder button (which adds the same items to cart if still available) are present.
7.2.4 Wishlist Sync, Coupons, Returns, Notifications
The account wishlist (/account/wishlist) is the server-side view of the wishlist described in Section 6.2. The coupons page (/account/coupons) shows coupons saved to the user's wallet (issued by the admin or auto-issued by marketing rules) with validity, value, and a Copy & Apply to Cart action. The returns page (/account/returns) lists return requests with status, reason, refund method, and amount. Notifications preferences (/account/notifications — Phase 2) controls channels (SMS, email, WhatsApp) and event types (order, offers, festival).
7.3 Guest Order Tracking
The /track-order page allows a guest customer to track an order without logging in by entering the order ID (from confirmation email/SMS) and the delivery phone number or email. The backend validates the combination and returns the same order detail view that an authenticated user would see for their own order. This route is publicly accessible but rate-limited (5 attempts per minute per IP).
7.4 Authentication Edge Cases
(1) Expired OTP — show a Resend OTP link with a cooldown timer (60 seconds between resends, max 5 resends per number per hour). (2) Account lockout after 5 failed login attempts — show a clear message and offer forgot-password. (3) Session expired mid-checkout — show a modal that allows re-login without losing the cart contents (cart is persisted client-side and re-merged on re-login). (4) Social login email conflict (Phase 2) — if a Google-login email matches an existing account, prompt for password to confirm ownership before linking. (5) Refresh token invalidation (e.g. user logged out from another device) — redirect to /auth/login with a Session Expired notice.

Admin sessions are short-lived (15-minute access TTL, 4-hour refresh TTL) and require re-authentication after 4 hours of inactivity. Two-factor authentication (TOTP via authenticator app) is mandatory for the super-admin role and recommended for all roles in Phase 2.

8.2 Admin Dashboard Home
The dashboard home (/admin/dashboard) is the landing page after admin login. Anatomy: (1) top bar with logo, search across orders/customers/products, admin profile menu, notifications bell; (2) left sidebar navigation; (3) main content area arranged as KPI cards row (revenue today, revenue MTD, orders today, AOV, conversion rate, low-stock alert count), a revenue trend chart (last 30 days with comparison to previous 30 days), a two-column row with Top Products (table) and Top Categories (donut chart), and a Recent Orders table with status pills and a quick-action menu per order. Below: pending-orders alert strip and recent-reviews moderation queue.
8.3 Catalog → Products
The product list (/admin/catalog/products) is a DataTable with columns: image, name (with category sub-line), price (selling + MRP), stock status (in/low/out), status (active/draft/archived), updated-at, and actions (edit, duplicate, archive). Filters above the table: search by name or SKU, category dropdown, status dropdown, stock status dropdown. Bulk actions: edit status, bulk delete (archived only), bulk export CSV. Pagination is 25 per page with jump-to-page.
The product create/edit form (/admin/catalog/products/new and /admin/catalog/products/[id]) is a tabbed interface with tabs General, Variants, Images, Pricing, Inventory, SEO, Shipping, Status. General: name, slug (auto-generated from name, editable), short description, long description (rich text), category (multi-select with sub-category), brand (default Suvarna), tags. Variants: define variant axes (size for rings/bangles, material, colour) with per-variant SKU, price override, stock, and image. Images: multi-upload via drag-drop with thumbnail grid, primary image selector, alt text per image, image order. Pricing: selling price, MRP, cost price (admin only), tax slab (3% or 5% GST based on HSN), effective discount auto-calculated. Inventory: stock per variant, low-stock threshold, reorder point, warehouse location. SEO: meta title, meta description, URL slug, canonical URL, schema override. Shipping: weight, dimensions, HSN code, hazardous flag. Status: draft, active, archived — with effective-from/effective-to scheduling (Phase 2).
8.4 Catalog → Categories
The categories page (/admin/catalog/categories) renders the category tree as a draggable nested list. Each node shows name, image, slug, product count, and a status toggle. CRUD actions support parent/child relationships (depth ≤ 2), image upload (square 256px), display order (auto-set by drag, manual override), and an optional SEO description. Deleting a category with active products is blocked; the admin must reassign products to another category before deletion.
8.5 Catalog → Collections
Collections (/admin/catalog/collections) are curated merchandising groups that span categories (e.g. Aishwarya Festive 2026, Bridal Couture, Daily Wear Essentials). CRUD with name, slug, description, hero image, scheduled publish window, and product selection (search-add products to the collection with manual ordering).
8.6 Inventory
The inventory view (/admin/catalog/inventory) is a stock ledger per SKU showing current stock, committed (in unpaid/pending orders), available, and a transaction history (adjustment reasons: receipt, damage, loss, transfer). Bulk import via CSV and bulk export are supported. Low-stock rules are configurable per product (alert threshold, reorder point) and trigger email notifications to the configured inventory manager.
8.7 Orders
The order list (/admin/orders) is a DataTable with columns: order ID, customer name, items (count + first 3 thumbnails), total, payment status, fulfilment status, channel (web/phone), placed-at. Filters: status, payment status, date range, channel. The order detail view (/admin/orders/[id]) shows: customer info (with link to customer detail), shipping address, items with quantities and totals, payment summary, fulfilment timeline (vertical stepper matching the customer-facing timeline), and an Actions panel with: Confirm Order, Pack Order, Mark Shipped (opens carrier + tracking-number form), Mark Out-for-Delivery (auto from carrier webhook), Mark Delivered (auto or manual), Cancel Order (with reason), Initiate Refund (with reason and refund-method dropdown), and Add Internal Note. Invoice print (PDF download) and Packing Slip print (PDF download) actions are available.
8.8 Customers
The customer list (/admin/customers) shows name, email, phone, orders count, total spent, last order date, segment, tags, and status (active/blacklisted). The customer detail view (/admin/customers/[id]) shows profile, address book, full order history with status, support tickets (Phase 2), segment membership, tags (admin-managed), and a blacklist toggle (with reason and reactivation). Blacklisting blocks new orders from that customer; existing pending orders are not auto-cancelled but flagged for review.
8.9 Coupons & Offers
The coupons module (/admin/marketing/coupons) is a CRUD interface for promotional codes. Coupon types: percentage off, flat amount off, free shipping, buy-one-get-one (Phase 2). Coupon rules: code (admin-set or auto-generated), description, type, value, min order amount, max discount amount, applicable categories (multi-select), applicable products (multi-select), valid-from, valid-to, usage cap (total), per-customer cap, first-order-only flag, customer segment (all, new, returning, VIP). A preview-and-test feature allows the admin to validate a coupon against a hypothetical cart before publishing. Coupon status: draft, active, paused, expired.
8.10 Reviews
The reviews moderation queue (/admin/catalog/reviews) lists pending reviews with reviewer name, product, rating, title, body, photos, and actions: Approve, Reject (with reason), Reply (admin response shown alongside the customer review on PDP), Report Spam (auto-flag pattern-based). Filtered views: pending, approved, rejected, flagged. Bulk actions: approve-all, reject-all (with confirmation).
8.11 CMS Pages, Banners & Settings
CMS pages (/admin/cms/pages) is a CRUD for static pages with rich-text editor (TipTap or Quill), slug, SEO meta, and status. Banners (/admin/cms/banners) manages hero carousel slides (image, mobile image, title, subtitle, link, scheduling, order) and mid-page feature blocks. Settings (/admin/settings) is a tabbed form covering store info (name, legal name, GSTIN, PAN, address, support contacts), currency (default INR), tax (GST slabs by HSN), shipping rules (free-shipping threshold, flat rates, pincode serviceability file upload), payment gateways (Razorpay/Cashfree key entry with secret masking), SEO defaults, email templates (order confirmation, shipping, delivery, abandoned cart), SMS templates (OTP, order status), and integrations (GA4, Meta Pixel, GTM container ID).

9.7 Responsive Breakpoints
The site is mobile-first with breakpoints aligned to Tailwind defaults: sm 640px (large phones landscape, small tablets), md 768px (tablets), lg 1024px (small laptops), xl 1280px (desktops), 2xl 1536px (large desktops, used for PDP and admin tables). 9.8 Motion & Animation
Motion is restrained and editorial — jewellery is a considered purchase, not an impulse buy, so motion must reinforce trust rather than urgency. Duration tokens: fast 150ms (hover, focus, toggle), normal 250ms (page transition, drawer open), slow 400ms (carousel slide, image zoom). Easing: ease-out for entries, ease-in for exits, ease-in-out for state changes. Specific patterns: product cards lift on hover (translateY -2px + shadow-lg), PDP main image zooms on hover (scale 1.08 over 400ms), drawers slide in from the right over 250ms, skeletons shimmer at 1.5s loop. prefers-reduced-motion media query is respected — all non-essential animations are disabled and instant transitions replace them.
9.9 Empty & Error States
Empty states (empty cart, no search results, no orders yet) use a small custom illustration (line-art, single-colour maroon on ivory) with a headline, a supportive sub-line, and a primary CTA. Error states (network failure, server error, not found) use the same illustration style with appropriate copy and a retry or back-home CTA. The 404 page uses a witty jewellery-themed line (e.g. This page has slipped off like a bangle.) with a search bar and the primary nav.
9.10 Brand Voice & Microcopy
Brand voice is warm, considered, and quietly confident — never shouty, never apologetic. Microcopy avoids discount-driven urgency (no Last 5 left!; no Hurry!); uses we and you; addresses the customer as someone choosing an heirloom, not chasing a deal. Microcopy examples: Add to Cart (not Add to Bag), Buy Now (not Grab Yours), Save for Later (not Move to Saved), Estimated delivery by 24 October (not Arrives soon). All copy is externalised in /locales/en.json for Phase 2 i18n.

11. State Management, Forms, Validation, Error Handling, Loading & Accessibility
11.1 State Management Strategy
The state strategy separates concerns by lifetime and origin: server state is owned by TanStack Query; ephemeral client UI state is owned by Zustand; URL-serialisable state (filters, pagination, sort) is owned by Next.js searchParams; form state is owned by react-hook-form; auth token state is owned by a Zustand store that synchronises with the httpOnly refresh cookie. This separation prevents the most common React-state anti-patterns (server data in client state, URL-derivable state in useState, form state duplicated in store).
TanStack Query is configured with: default staleTime 60 seconds, gcTime 5 minutes, retry (1 retry with exponential backoff for 5xx errors, 0 retries for 4xx), refetchOnWindowFocus false (avoid unnecessary refetches on tab focus), refetchOnReconnect true. Mutations implement optimistic updates with rollback on error; the cart add/remove flow uses this pattern so the UI updates instantly and rolls back if the server rejects. Query keys are structured hierarchically (['products', { category, page, filters }]) to enable targeted invalidation after mutations.
Zustand stores are: uiStore (cart drawer open, search overlay open, mobile nav open, theme); authStore (user object, accessToken, isAuthenticated, loginInProgress flag); wishlistStore (hydrated from server for authed users, localStorage for guests). All stores are persisted only where necessary (wishlist and guest cart to localStorage with a 7-day TTL); authStore is persisted to sessionStorage only for the access token to survive reload during a session, with the refresh cookie providing re-auth.
11.2 Form Validation
Forms use react-hook-form for state management and zod for schema validation. The same zod schemas are shared between client and (eventually) backend, ensuring a single source of truth for shape and constraint. Validation is field-level on blur, submit-blocked on invalid, and accessible — every error is associated with its input via aria-describedby, the error container has role="status" for screen-reader announcement, and the submit button shows a disabled state until the form is valid.
India-specific validation rules: phone numbers must match ^+91[6-9]\d{9}$ (Indian mobile numbers start with 6, 7, 8, or 9); pincodes must match ^\d{6}$; GSTIN must match the 15-character pattern with check-digit validation; email must be a valid RFC 5322 address. Password rules: minimum 8 characters, at least 1 letter and 1 number (Phase 2 may enforce special characters). The OTP input component enforces numeric-only input with auto-advance and paste-distribution across the 6 boxes.
11.3 Error Handling
The error-handling strategy normalises backend errors into a predictable client-side shape and routes them to the appropriate UI surface. Every API call is wrapped in a typed fetcher that catches network errors, HTTP errors, and parse errors, and emits an ApiError of the form { code, message, fieldErrors?, traceId }. The fetcher integrates with TanStack Query's onError to fire toasts for actionable errors and with the global ErrorBoundary for unrecoverable errors.

11.4 Loading States
Every async surface MUST show a loading state — there is no acceptable blank state during a fetch. Patterns: (1) Skeleton loaders for grid lists (ProductCardSkeleton mimics the card shape with shimmer animation); (2) Inline spinners for action buttons (Add to Cart shows a 16px spinner for the 200ms request); (3) Disabled-with-spinner for submit buttons (Place Order disabled + spinner during payment initiation); (4) Optimistic UI for cart/wishlist toggles (the heart icon fills instantly and rolls back on error); (5) Suspense boundaries for route transitions with a branded fallback. Page-level Suspense fallbacks are minimal branded loaders; component-level Suspense fallbacks are skeletons.
11.5 Accessibility (WCAG 2.1 AA)
Accessibility is a launch-blocking requirement, not a post-launch enhancement. The target conformance level is WCAG 2.1 AA. The implementation MUST pass an axe-core audit in CI with zero serious or critical violations on all storefront routes. Specific requirements:
Semantic HTML throughout — use <button> for actions (not <div onClick>), <a> for navigation, <form> for forms, <nav>, <main>, <article>, <section> with aria-label where appropriate.
ARIA roles only where native semantics are insufficient — drawer (role="dialog" aria-modal="true"), dropdown (role="listbox"), tabs (role="tablist" with aria-selected), accordion (aria-expanded on header).
Keyboard navigation: all interactive elements reachable via Tab in logical order; visible focus rings (2px antique-gold outline, never removed); Escape closes overlays and returns focus to trigger; focus trap inside Modal and Drawer; focus returns to trigger on close.
Colour contrast: text-on-background meets 4.5:1 (normal text) and 3:1 (large text). The maroon-on-ivory primary combination meets 7.1:1; antique-gold-on-charcoal meets 4.6:1.
Alt text on every meaningful image; decorative images use alt=""; product images have alt text written by content-editors.
Form labels: every input has a programmatically associated <label> (htmlFor or aria-labelledby); errors are announced via aria-describedby pointing to error container with role="status".
Skip-to-content link at the top of every page (visible on focus) to bypass repeated header navigation.
prefers-reduced-motion respected — all non-essential animations disabled when the user has set this preference.
Screen reader testing: NVDA on Windows + VoiceOver on macOS tested for the critical flows (homepage, PDP, cart, checkout, account) before launch.
11.6 Internationalisation Readiness
Although the MVP launches in English only, the codebase is structured for i18n from day one. All user-facing strings are externalised into /locales/en.json; the next-intl library is installed but only English is configured at launch. 12. REST API Integration Contract (Frontend ↔ Backend)
12.1 API Conventions
This section defines the contract the frontend expects from the Node.js + Express backend. The backend team and the coding agent MUST implement exactly this contract. Any deviation requires explicit negotiation and an update to this specification. The conventions are: (1) base URL via NEXT_PUBLIC_API_BASE_URL with /api/v1 version prefix; (2) request and response bodies are JSON with Content-Type: application/json; (3) authentication uses Bearer JWT access tokens in the Authorization header for storefront endpoints and a separate cookie-based admin JWT for admin endpoints; (4) refresh tokens travel in httpOnly cookies set by the backend and are never read by frontend JavaScript; (5) idempotency keys are sent via the Idempotency-Key header on POST /orders and POST /checkout/payment/initiate to prevent duplicate orders on retry.
Standard error envelope: { error: { code: string, message: string, fieldErrors?: Array<{field, message}>, traceId: string } }. 12.3 Admin API Contract Pattern
Admin endpoints live under /api/v1/admin/* and follow the same conventions but require an admin JWT (separate cookie) and pass through the PermissionGate middleware on the backend that checks role-permission per route. The admin endpoint inventory mirrors the admin routes in Table 8.2 and is implemented as: GET/POST/PATCH/DELETE /admin/products, /admin/categories, /admin/orders, /admin/customers, /admin/coupons, /admin/reviews, /admin/pages, /admin/banners, /admin/settings (PATCH only), /admin/users (super-admin only). Each list endpoint supports the same pagination envelope and a total summary for dashboard KPIs.
12.4 File Upload Contract
Image uploads (admin product images, banner images, customer review photos) use a presigned-URL flow: the client calls POST /api/v1/admin/uploads/request with { filename, contentType, size } and receives a presigned S3 URL + an assetId; the client then PUTs the file directly to S3 (bypassing the backend for the binary blob) and calls POST /api/v1/admin/uploads/confirm with the assetId to register the upload. This pattern keeps the backend stateless for binary traffic and limits the backend's exposure to large request bodies. The backend validates MIME type, file size, and magic bytes before issuing the presigned URL.
12.5 Real-time Order Status (Phase 2)
In the MVP, order status updates are delivered via polling — the customer's order detail page refetches the order every 30 seconds when the tab is visible. Phase 2 introduces a WebSocket connection at /realtime that pushes order status events ({ orderId, status, timestamp, message }) to authenticated customers. The frontend integrates via a useOrderStatus hook that abstracts the transport so the polling-to-WebSocket migration is invisible to the UI.
12.6 Backend-Enforced Controls (Reminder)
The frontend cannot be trusted with security or data-integrity decisions. The backend MUST enforce: server-side price recompute on order creation (never trust the cart total sent by the client), server-authoritative stock check (re-validate availability at order creation; if stock has dropped since cart add, fail the order with a clear message), coupon validation (re-validate coupon eligibility, expiry, usage cap), idempotency-key enforcement on POST /orders and POST /checkout/payment/initiate (return the original response on duplicate), and audit logging of all admin actions. These are non-negotiable and are restated here because they shape the frontend's responsibility boundary in Section 13.
13. Security — Frontend Responsibilities & Backend-Enforced Controls
This section deliberately splits security into two columns: what the frontend MUST do (defence in depth, UX) and what the backend MUST enforce (the actual security boundary). The fundamental principle: the frontend is untrusted code running on a customer's device; the backend is the only authoritative source of truth. No security decision can rely on the frontend doing or not doing something.

NEVER log card numbers, CVV, or full card data; the application MUST be out of PCI scope by design via hosted-fields integration

13.3 Trust Boundary Statement
To remove any ambiguity: the frontend is untrusted code. Any check the frontend performs is for UX, not for security. Every security decision is re-made by the backend on the corresponding endpoint. The frontend cannot prevent a customer from calling POST /api/v1/checkout/payment/initiate with a tampered cart total — the backend MUST reject it. The frontend cannot prevent a customer from calling GET /api/v1/admin/orders — the backend MUST reject it. The frontend cannot prevent a customer from reusing an old OTP — the backend MUST reject it. The implementation MUST be reviewed against this principle before launch.
14. SEO, Performance, Mobile Responsiveness, Testing & Deployment
14.1 Search Engine Optimisation
SEO is a launch-blocking requirement for an e-commerce site because organic search is a primary acquisition channel for jewellery queries in India. The render strategy per route is defined in Table 3.1; the most SEO-critical routes — homepage, PLP, PDP — use SSG with ISR to ensure fast first paint and fresh content. The Next.js Metadata API is used to set title, description, open-graph, Twitter card, canonical, robots, and hreflang per route. The metadata is generated dynamically from the admin-managed SEO fields (meta title, meta description, canonical) with sensible fallbacks for routes without explicit overrides.
Structured data via JSON-LD is embedded on the relevant routes: Organization + WebSite + SearchAction on the homepage; BreadcrumbList on all routes with breadcrumbs; ItemList on PLPs; Product + Offer + AggregateRating + Review on PDPs; FAQPage on policy pages that include FAQ sections. The schema is validated via Google's Rich Results Test before launch.
A sitemap.xml is generated dynamically from the backend GET /api/v1/sitemap endpoint (which enumerates products, categories, collections, and CMS pages with their last-modified dates) and submitted to Google Search Console. A robots.txt allows all storefront routes and disallows /admin/, /account/, /checkout/, /auth/. Canonical URLs prevent duplicate content from query parameters — filter URLs include rel=canonical pointing to the base PLP. hreflang tags are stubbed for en only at MVP and extended in Phase 2 when Hindi is added.

The storefront is mobile-first because the majority of Indian e-commerce traffic is on mobile. The implementation MUST: target 360–414px width as the primary device class; ensure all touch targets are at least 44×44px (Apple HIG) and 48×48px (Google Material) with adequate spacing; implement a sticky bottom add-to-cart bar on mobile PDPs that becomes visible on scroll-past the in-content add-to-cart button; render filters as a bottom-sheet rather than a sidebar on mobile; implement swipeable image gallery with native touch gestures; respect safe-area-insets for notched devices (iPhone X+); disable pull-to-refresh only where it conflicts with custom gestures; and test on real devices (at minimum one Android mid-range + one iPhone) before launch.
14.4 Testing Strategy
The testing strategy has four layers. (1) Unit tests with Vitest cover utility functions, zod schemas, and pure hooks (formatINR, useCart calculations, validators). Coverage target: 80% on lib/ folders. (2) Component tests with React Testing Library + Vitest cover the component library — every component has at least one render test and one interaction test. Coverage target: 70% on components/. (3) Integration tests with Playwright cover the critical flows in Section 17 (registration + first order, login + checkout, guest checkout, admin fulfilment, payment failure recovery, out-of-stock mid-checkout). (4) Accessibility audit with axe-core runs in CI on every PR and fails the build on serious or critical violations.
Lighthouse CI is configured to run on every PR against a preview deployment and enforces thresholds: Performance ≥ 90, Accessibility ≥ 95, Best Practices ≥ 95, SEO ≥ 95 on the homepage, a sample PLP, and a sample PDP (mobile emulation). Visual regression with Chromatic or Percy is a Phase 2 enhancement. Load testing with k6 simulates 1000 concurrent users on the homepage and 100 concurrent users on checkout before launch; targets: P95 response time < 2s for homepage, < 3s for checkout initiation under load.
14.5 Build & Deployment
The build pipeline: lint (eslint + prettier), type-check (tsc --noEmit), unit tests, component tests, build (next build), Playwright smoke tests against a built preview, Lighthouse CI, deploy. Environment variables are differentiated across dev/stage/prod via a NEXT_PUBLIC_ENV variable and server-side secrets managed via the deployment platform (Vercel for MVP, or a self-managed Node.js host with PM2 + nginx if client requires). Preview deployments are auto-created per PR and shared with the client for review.
Static assets (next/image outputs, fonts, favicons) are served via a CDN with cache-control: public, max-age=31536000, immutable for hashed assets and no-cache for HTML. Product images are served via an image CDN (Cloudinary, ImageKit, or AWS CloudFront + Lambda Sharp) with on-the-fly resizing and WebP/AVIF format negotiation. Monitoring: Sentry for runtime errors with source-map upload, Vercel Web Analytics or GA4 for product analytics, Better Uptime or UptimeRobot for uptime monitoring (1-min interval on /api/v1/health), structured logging on the backend (pino) shipped to a log aggregator. Rollback strategy: Vercel instant rollback to previous deployment; for self-managed, blue-green deployment via PM2 reload.
15. Edge Cases & Acceptance Criteria
15.1 Cart Edge Cases
(1) Add out-of-stock item — frontend SHOULD block the Add-to-Cart click and show Notify Me instead; backend MUST reject POST /cart/items for out-of-stock products with 422. (2) Quantity exceeds available stock — frontend stepper disables at max-available; backend rejects PATCH with quantity > stock with 422. (3) Variant no longer available — on PDP load, if the variant referenced by URL is archived, redirect to the canonical product URL and show a toast. (4) Coupon expired mid-session — on /cart/apply-coupon returning 422, show toast Coupon expired, remove applied coupon from cart state, recompute totals. (5) Price changed between add-to-cart and checkout — on /checkout/quote returning a different total than the cart shows, show Price Change notice and require Re-accept before Place Order. (6) Guest cart merge on login — on successful login, POST /cart/merge merges guest cart into server cart; conflicts (same product, different variants) are summed with max-per-order cap.
15.2 Checkout Edge Cases
(1) Pincode serviceable check fails — block navigation to step 2; suggest nearby serviceable pincodes if available (via GET /pincode/nearby?q=). (2) Payment gateway timeout — frontend shows Payment Being Processed screen and polls /checkout/payment/verify every 5s for 5 minutes; on timeout, instructs user to check email; backend reconciliation webhook from gateway finalises the order within 24h. (3) Payment success but order creation failure — backend reconciliation catches this via gateway webhook; the order is auto-created from the webhook payload; the customer sees Payment Received, Order Being Confirmed state. (4) Address validation fails — inline errors per field; pincode field auto-fetches city/state and rejects pincodes that do not match the regex. (5) COD not available for pincode — COD radio hidden on step 2 based on /checkout/quote response. (6) Order placed but confirmation email delayed — show order confirmation page regardless; email is best-effort; the order is visible in /account/orders or /track-order immediately.
15.3 Authentication Edge Cases
(1) Register with existing email — backend returns 409; frontend shows inline error Email already registered; offer login link. (2) OTP brute force — backend rate-limits; on 429, frontend disables Resend OTP for retry-after seconds. (3) Session expired mid-checkout — modal Session Expired with Re-login button; cart is preserved client-side and re-synced on re-login; checkout flow resumes at the same step. (4) Refresh token stolen — single-use refresh detects reuse and invalidates the entire token family; user is logged out across all devices. (5) Social login email conflict (Phase 2) — show This email is registered; please log in with password to confirm ownership.
15.4 Product Edge Cases
(1) PDP for archived product — backend returns 410 Gone with a Location header pointing to the category; frontend renders a PDP with This product is no longer available and a Shop Similar Products rail. (2) PDP slug changed — backend maintains a slug-redirect table; on GET /products/:slug returning 301 with Location, frontend follows and Next.js rewrites the URL. (3) Variant sold out after add-to-cart — on next page load or cart refetch, the variant shows as Out of Stock in the cart with a Remove option; backend blocks checkout with a clear message.
15.5 Admin Edge Cases
(1) Concurrent edits to the same product — backend uses optimistic locking (updated_at timestamp); on PATCH returning 409, frontend shows Another admin edited this product; reload to see their changes. (2) Deleting a category with active products — backend returns 409 with the count of affected products; frontend prompts the admin to reassign before deletion. (3) Refund for already-refunded order — backend returns 422; frontend disables the Refund button if order status is refunded. (4) Bulk action exceeding limit — backend rejects with 413; frontend splits the action into batches of 25.

16.1 Phase Dependencies & Rationale
The MVP features are sequenced for the smallest viable launch: catalogue management is built first because it is the data backbone; storefront and cart follow because they exercise the catalogue; checkout and payment are added once cart is stable; admin fulfilment is added once orders can be placed. Phase 2 features are sequenced by ROI: abandoned cart recovery has the highest revenue impact, followed by additional payment methods and Hindi localisation. Phase 3 features are sequenced by strategic value: loyalty programme and referral are the strongest retention levers; native apps are the largest engineering investment and are deferred until the web experience is mature.
17. Critical Flow Acceptance Test Cases
The following test cases are the acceptance criteria for the six critical flows. They are written in Given/When/Then format and MUST pass in CI before launch. Each test case is implemented as a Playwright spec in /tests/e2e/.
17.1 New Customer Registration → First Successful Order
Given: a fresh browser session with no existing account; the cart is empty; the test product (Gold Jhumka SKU TEST-001) is in stock at ₹1,499.
When: the customer navigates to /auth/register, enters full name + phone + password, receives OTP via test-mode SMS, enters OTP, and submits; then navigates to /shop/jhumkas, opens the test PDP, selects size M, clicks Add to Cart, opens /cart, applies coupon WELCOME10 (10% off first order), proceeds to /checkout/address, enters a serviceable address, selects UPI payment, completes payment in test mode, and lands on /order/confirm/[id].
Then: the order is created with status placed; the cart is cleared; the coupon usage is recorded (first-order-only flag is set); the order appears in /account/orders; a confirmation email is queued; the customer receives a success toast and the order confirmation page shows the correct estimated delivery date. Exit criteria: order ID matches between confirmation page, account order history, and admin order list.
17.2 Returning Customer — Login → Cart → Coupon → Checkout → Payment
Given: an existing customer with a verified phone, at least one past order, and an address in their address book; the test product is in stock.
When: the customer navigates to /auth/login, enters phone + password, logs in; visits the wishlist, moves one item to cart; applies a coupon; proceeds to checkout; selects the saved address; selects card payment; completes payment; lands on confirmation.
Then: the cart line items, address, payment method, coupon, and total are all correctly reflected on the confirmation page; the order appears in account history with status paid. Exit criteria: order total = (item subtotal − coupon discount + shipping + tax).
17.3 Guest Checkout with COD → Confirmation → Track Order
Given: a fresh browser session with no account; the test product supports COD for the test pincode.
When: the guest adds a product to cart, navigates to /cart, proceeds to checkout as guest, enters a new address in a COD-serviceable pincode, selects COD payment, places order, lands on confirmation.
Then: the order is created with payment_status = pending_cod and status = placed; a confirmation email is sent; the guest navigates to /track-order, enters order ID + phone, and sees the order detail. Exit criteria: order is visible in track-order without requiring login.
17.4 Admin Order Fulfilment End-to-End
Given: an admin (manager role) is logged in; a new order exists in placed status.
When: the admin navigates to /admin/orders, opens the order detail, clicks Confirm Order, then Pack Order, then Mark Shipped (enters carrier and tracking number), then Mark Delivered (manual or via carrier webhook).
Then: each transition updates the order status in the database and the customer-facing timeline; the customer's /account/orders/[id] page shows the timeline step change in real time (or on next poll). Exit criteria: timeline shows all six stages with timestamps; invoice and packing slip PDFs download successfully.
17.5 Payment Failure → Retry → Success
Given: a customer at the payment step of checkout with a valid cart and address.
When: the customer triggers payment via card, the gateway returns a failure (test mode mock), the customer sees the failure screen with a Retry button; the customer retries with a different payment method (UPI) and the gateway returns success.
Then: the failed payment attempt is logged but no order is created (idempotency); the successful payment creates exactly one order; the cart is cleared only after success. Exit criteria: no duplicate order; customer sees confirmation page; no double-charge in the gateway dashboard.
17.6 Out-of-Stock Mid-Checkout
Given: a customer has added a product to cart with quantity 2, and stock is 1.
When: the stock drops to 0 (admin adjusts inventory or another customer purchases the last unit) before the customer reaches the Place Order step; the customer clicks Place Order.
Then: the backend returns 422 with a clear message; the frontend shows a modal Item no longer in stock, redirects to /cart with the affected item flagged, and offers replacement suggestions. Exit criteria: no order is created; customer is clearly informed; cart is in a recoverable state.
17.7 Concurrent Admin Edit (Optimistic Locking)
Given: two admin sessions (manager A and manager B) are both editing the same product.
When: manager A saves first; manager B saves second without reloading.
Then: manager B receives a 409 conflict response; the frontend shows Another admin edited this product. Reload to see their changes. and discards manager B's changes. Exit criteria: the database reflects manager A's version; no silent overwrite.
17.8 Session Expired Mid-Checkout Recovery
Given: a customer is on the Review step of checkout and their access token expires (TTL 15min reached).
When: the customer clicks Place Order; the fetch returns 401; the silent refresh attempt also fails (refresh token expired).
Then: a modal Session Expired appears with a Re-login button; the cart is preserved in localStorage; on re-login, the cart is re-synced and the customer returns to the same checkout step with all data preserved. Exit criteria: no data loss; the customer can complete the order without re-entering cart or address.
